- 작성일: 2026-11-15 (같은 날 개정: BGG API 사용 불가 → Gemini 지식 기반 게임 소개 + 필요한 질문에만 실시간 웹 검색)
- 상태: 승인됨 (2026-11-15)
- 이전 설계: [2026-11-14-natural-language-search-design.md](2026-11-14-natural-language-search-design.md) (이 문서는 그 위에 쌓는다. 여기서 바꾸지 않은 내용은 그대로 유효)

## 1. 의도와 이유

사람이 보드게임에 대해 할 법한 **대부분의 질문**에 의미가 맞는 게임을 추천하고 싶다. 예:

- 누구와·어떤 자리: "할머니, 할아버지와 함께하기 좋은 게임", "어린아이들과 하기 좋은 동물이 나오는 게임", "술자리에서"
- 느낌·분위기: "긴장감 있는", "머리 안 쓰는"
- 장르: "전쟁 게임"
- 순위: "가장 유명한 게임"
- 데이터 밖의 사실: "스타워즈 테마의 보드게임", "한국인이 만든 보드게임"
- 답이 없는 질문: "동물들도 이해하기 쉬운 게임"

지금 방식의 한계 (2026-11-15 코드·데이터 확인):

1. **결과를 검증하는 단계가 없다.** Gemini 조건 추출 → 설명글 임베딩 유사도 → 고정 공식(`0.75·유사도 + 0.25·평점`). 유사도를 후보 안 중앙값~최댓값으로 환산하므로, 맞는 게임이 없어도 1위는 높은 점수를 받는다. 실패 유형마다 특별 규칙을 덧대 왔고, 이 방식은 "모든 질문"으로 확장되지 않는다.
2. **문서가 경험이 아니라 배경 이야기를 담는다.** BGG 설명글은 대부분 설정·홍보 문구다. 질문은 "누구와, 어떤 느낌"을 묻는다.
3. **쓸 수 있는 데이터를 안 쓴다.** `features.load_games()`가 이미 `Family`, `Cat:*`를 붙이지만 자연어 검색은 쓰지 않는다. 원본 `games.csv`의 권장 연령(`ComAgeRec`), 언어 의존도(`LanguageEase`), 인원별 평가(`GoodPlayers`)도 후보 2,906개(리뷰 1,000개 이상) 거의 전부에 값이 있다.
4. **데이터에 없는 사실이 있다.** 디자이너·출판사·국가 정보가 없다. 스타워즈는 후보 중 23개가 이름에, 29개가 설명글에 있지만, 추출 프롬프트의 "고유명사를 쓰지 마라" 규칙이 검색문에서 "Star Wars"를 지운다.
5. **같은 게임의 다른 버전이 섞인다.** 후보 안에 Carcassonne 계열 17개, Ticket to Ride 13개, Pandemic 12개. `Family` 열은 값이 하나뿐이고 잘려 있으며("Carcassonn"), 후보 1,318개는 비어 있고, 출판사 라인("Two-player games (Kosmos)")이 섞여 있다.
6. **태그에 오류가 있다.** 예: Connect Four가 "동물 테마 + 어린이 분류"로 표시됨. 태그만 믿으면 이런 게임이 섞인다.
7. **품질을 재는 기준이 없다.**

## 2. 목표 / 비목표 / 실패 기준

### 목표
1. 위 질문 유형에 대해 평가 세트로 **측정 가능한** 정확도 향상
2. 결과 5개 안에 같은 시리즈는 **대표 하나만** (사용자 결정)
3. 데이터 밖 사실(프랜차이즈, 원작 게임, 디자이너, 디자이너 국적)을 Gemini 지식으로 한 번 채워 질의에 사용
4. 그래도 데이터로 답하기 어려운 질문은 **그 질문에만 실시간 웹 검색** (사용자 결정)
5. 답이 애매하거나 없는 질문에는 **어떻게 해석했는지** 화면에 보여주고, 가까운 결과가 약하면 알림
6. Gemini 예산 약 6,000원 안에서 개발과 초기 서비스 운영 (사용자 제약)

### 비목표 (이번 범위 밖)
- BGG XML API 사용 (사용자가 키 발급 불가)
- 웹 검색 결과를 저장해 두고 쓰는 방식 (약관 금지, 3장)
- 검색어 안의 기준 게임 인식("카탄 같은데 더 가벼운"). "By game" 탭이 맡는다 *(내 판단)*
- 2021년 이후 게임, 리뷰 1,000개 미만 게임 (데이터 한계)
- 장르 화면, "By game" 추천의 결과 묶기 *(내 판단)*
- 상세 팝업의 "Other versions" 목록 (BGG 데이터 없이 시리즈 정보 정확도가 낮아 이번엔 뺀다. 숨겨진 버전은 이름 검색으로 찾을 수 있다) *(내 판단)*

### 실패 기준
- 맞는 게임이 없는 질문에 아무 설명 없이 결과 5개를 자신 있게 보여줌
- 화면에 보이는 해석 문장이나 추천 이유가 데이터에 없는 사실을 지어냄
- 재정렬·웹 검색이 실패할 때 검색 자체가 깨짐 (지금 방식으로 물러나야 함)
- 기존 기능(이름 검색, By game, 장르 화면)에 영향
- 화면에 한국어 문장이 나옴
- 웹 검색이 필요 없는 질문의 첫 검색이 지금보다 +2초 넘게 느려짐 (보통의 경우 기준)
- **웹 검색 약관 위반**: 웹 검색 결과를 저장·캐시하거나, 검색 제안 없이 보여주거나, 질문한 사용자 외에게 보여줌
- CI가 Gemini 키를 필요로 하게 됨
- 예산 초과 (Google 쪽 예산 알림과 일일 상한으로 막는다)

## 3. 제약

이전 설계 3장 그대로 (Cloud Run 1Gi, 데이터 파일은 git 커밋, CI에 키 없음, Gemini 유료, 인스턴스당 일일 호출 상한 `gemini.charge()`). 추가로:

- 후보 게임은 리뷰 1,000개 이상 2,906개
- **예산 약 6,000원** (환율 약 1,450원/$). 예상 배분 (2026-11-15 요금 기준 추정):

  | 항목 | 예상 |
  | --- | --- |
  | 평가 약 6회 (질의 40개, 해석 결과 재사용) | 1,200~1,800원 |
  | 게임 소개 만들기 + 다시 임베딩 (한 번) | 900~2,000원 |
  | 동작 확인 | 약 200원 |
  | 서비스 검색 1회 | 재정렬 없음 약 5원 / 있음 약 7원 |
  | 웹 검색 | 매달 5,000회까지 무료, 이후 1,000회당 $14 (1회 약 20원) |

- **웹 검색(Grounding with Google Search) 약관** ([Gemini API Additional Terms](https://ai.google.dev/gemini-api/terms), 2026-11-15 확인):
  - 웹 검색 결과와 검색 제안을 캐시·저장·분석·학습에 쓰면 안 된다 (법적 의무를 위한 최소 보관만 허용)
  - 결과는 질문한 사용자에게만, Google이 주는 검색 제안과 함께 보여줘야 한다 (위젯을 고치지 않고 결과 옆에)
  - Google이 질문·결과를 30일 보관하며 끌 수 없다
  - **5단계 배포 전 사용자가 약관 전문을 직접 확인한다.** 이 설계는 위 해석을 기준으로 만든다
- 웹 검색은 Gemini 3 이상 모델에서 검색 횟수 기준 과금. 유료 등급 기본 한도 하루 1,500회
- 웹 검색과 JSON 형식 출력을 함께 쓰면 응답이 잘리거나 출처 정보가 빈다는 개발자 보고가 있다 → 웹 검색 호출은 **일반 텍스트**로 받는다

## 4. 검토한 방법

| 방법 | 내용 | 판단 |
| --- | --- | --- |
| 평가 세트 | 질의 + 정답 게임 + 측정 스크립트 | **채택** (모든 단계의 기준) |
| 이미 가진 데이터 + 키워드 + 단어 일치 | 연령·언어·인원 적합도·분류, 고유명사 키워드, TF-IDF 단어 일치를 점수에 섞음 | **채택** (비용 0) |
| 게임 소개 (Gemini 지식) | 게임마다 경험 소개 + 프랜차이즈·원작·디자이너·국적을 한 번 생성, 소개로 다시 임베딩 | **채택** (검색 시 비용 0) |
| LLM 재정렬 | 상위 후보를 Gemini가 질의에 맞게 다시 고르고 해석 문장 생성 | **채택** (검색당 비용 있음, 크기는 평가로 결정) |
| 실시간 웹 검색 (필요한 질문만) | 질의 해석이 "외부 사실 필요"로 판단한 질문만 Google 검색 | **채택** (사용자 결정) |
| BGG API 보강 | 계열·디자이너·출판사를 BGG에서 수집 | 불가 (키 발급 불가) |
| 웹 검색으로 게임 소개 만들기 | 소개 생성 시 웹 검색 사용, 결과 저장 | 불가 (약관상 저장 금지) |
| 모든 질문에 웹 검색 | 질문마다 검색 | 기각 (지연·비용, 대부분 질문에 불필요) |
| Wikidata | 공개 DB의 디자이너·국가·시리즈 | 기각 (BGG ID 연결 5,266개 중 디자이너 약 110~250개, 한국 관련 0~3개로 너무 적음) |

**선택 (사용자 결정): 평가 세트 → 이미 가진 데이터 → 게임 소개 → 재정렬 → 필요한 질문에만 웹 검색.** 재정렬은 검색마다 비용이 드는 단계라, 앞 단계로 후보 뽑기를 먼저 좋게 만든 뒤 평가로 크기를 정한다.

## 5. 결정된 동작

단계마다 따로 PR로 합친다. 1~4단계 끝에 평가를 돌려 숫자를 기록한다 (5단계는 약관 때문에 자동 평가하지 않는다, 5.5).

### 5.1 1단계: 평가 세트

- 질의 파일 `data/natural_eval_queries.json`: **질의 40개**, 한국어·영어 섞어서, 유형별 4개 이상:
  누구와·어떤 자리(`audience`) / 느낌·분위기(`mood`) / 장르·메커니즘(`genre`) / 순위(`ranking`) / 데이터 밖 사실(`external`: 프랜차이즈, 디자이너, 국적) / 답이 없는 질문(`no_answer`) / 시리즈 중복이 잘 생기는 질의(`series`)
  1장의 예시 질문을 모두 포함한다
- 항목 형식:
  ```json
  {
    "query": "할머니, 할아버지와 함께하기 좋은 게임",
    "type": "audience",
    "players": 4, "max_time": 60,
    "good": [BGGId, ...],        // 이 중 하나 이상이 상위 5개에 있으면 적중
    "bad": [BGGId, ...],         // 나오면 안 되는 게임 (선택)
    "expect_weak_match": false   // 답이 없는 질문이면 true
  }
  ```
  `good`은 그 항목의 인원·시간 조건에서 후보가 될 수 있는 게임만
- 정답 목록은 **구현자가 초안을 만들고 사용자가 검토**한 뒤 확정 *(내 판단)*
- 측정 스크립트 `backend/evaluate_natural.py` (실제 키 필요, CI 아님). 출력: Hit@5, Precision@5, Recall@N(재정렬 전 후보 N개 안에 정답이 있는 비율), 시리즈 중복률, bad 노출 수, 답 없는 질문의 `weak_match` 비율. 전체와 유형별
- **비용 절약**: 질의 해석 결과와 질의 벡터를 로컬 파일(`data/natural_eval_cache.json`, git 제외)에 저장해 다시 쓰는 옵션. 해석 프롬프트를 바꾼 단계에서만 새로 받는다 *(내 판단)*
- 결과는 `data/natural_eval_results/<단계>.json`으로 저장, 커밋
- 첫 실행 = 지금 코드 그대로의 **기준선**

### 5.2 2단계: 이미 가진 데이터 + 키워드 + 단어 일치 + 시리즈 묶기

**데이터:** `load_games()`가 `ComAgeRec`, `LanguageEase`, `GoodPlayers`도 붙인다. `LanguageEase`는 척도가 문서와 달라 보여(21.15 같은 값) 후보 안 백분위로만 쓴다.

**조건 추출에 새 항목** (`QueryIntent`):
- `age_max`: "아이와", "8살" → 권장 연령 상한. 하드 필터, 값 없는 게임은 통과
- `categories`: `Cat:Family`/`Party`/`Childrens` 등 분류. 태그 일치에 포함
- `low_text`: "글 없는", "언어 몰라도" → `LanguageEase` 낮은 쪽 우대 (소프트)
- `keywords`: 질의의 **고유명사**(프랜차이즈, 디자이너, 출판사, 국가)를 영어 정식 이름으로. 예: 스타워즈 → "Star Wars", 한국 → "Korea". `search_text`의 고유명사 금지 규칙은 유지
- `terms`: 질의의 **구체적인 소재 단어**(영어). 예: "동물이 나오는" → "animals", "좀비" → "zombies". 단어 일치 점수에 쓴다
- 인원 적합도: 화면에서 고른 인원이 `GoodPlayers`에 있으면 소프트 가점 (항상)

**점수:**
- `keywords`: 이름·설명글에 단어 단위로 있으면 태그 일치로 센다 (3단계에서 게임 소개의 프랜차이즈·디자이너·국적과도 맞춘다)
- `terms`: 기존 TF-IDF(이름+설명글)로 후보마다 단어 일치 점수를 계산해 임베딩 유사도와 섞는다 (시작: `유사도 = 0.7·임베딩 + 0.15·태그 + 0.15·단어`)
- 최종 시작값: `0.65·유사도 + 0.2·평점 + 0.15·소프트`. 가중치는 평가로 조정

**시리즈 묶기 (임시 규칙):** 지금의 `Family` 열(출판사 라인 값은 묶지 않음) + 이름 앞부분(":" 앞이 다른 후보 게임 이름과 같으면 같은 시리즈). 3단계에서 게임 소개의 원작 정보로 보강
- **범위: 시리즈 전체** (사용자 결정). 후속작·스핀오프도 한 묶음 (Pandemic + Pandemic Legacy, Codenames + Codenames: Duet)
- **대표**: 같은 시리즈 후보 중 질의 태그·키워드와 가장 많이 맞는 버전들 중에서 리뷰가 가장 많은 버전. 순위 질의에서는 정렬 기준 값(리뷰 수·평점·연도)이 가장 높은 버전 *(내 판단)*
- 평가의 중복률과 `good` 목록도 이 범위를 따른다

### 5.3 3단계: 게임 소개 (Gemini 지식, 한 번만)

**생성 스크립트** `backend/build_game_profiles.py` → `data/game_profiles.json` (커밋)
- 대상: 리뷰 1,000개 이상 2,906개. 리뷰 많은 순으로 처리 (중간에 멈춰도 인기 게임부터 채워짐)
- **웹 검색 없음** (약관). Gemini가 아는 내용 + 우리 데이터(이름, 연도, 설명글, 메커니즘, 테마, 분류, 난이도, 권장 연령, 인원)를 근거로
- 한 요청에 게임 여러 개(시작 10개), 구조화 JSON. 게임마다:
  - `profile`: 영어 60~120단어. 누구에게 맞는지(연령, 가족, 커플, 파티, 숙련자), 어울리는 자리, 분위기, 상호작용 방식, 배우기 쉬운지, 한 판의 느낌
  - `franchise`: IP·프랜차이즈 (예: "Star Wars"), 없으면 빈 배열
  - `base_game`: 이 게임이 어느 게임의 다른 판·후속작·스핀오프인지 (게임 이름), 아니면 null
  - `designers`, `designer_countries`: 모르면 빈 배열
  - 프롬프트: 확실하지 않은 사실은 비워 둘 것, 소개는 주어진 데이터와 모순되지 않을 것
- 모델은 상수 `PROFILE_MODEL` (시작 `gemini-3.5-flash-lite`). 재시도·이어서 실행·진행 저장 지원
- **시험 실행**: 먼저 50개(인기·비인기 섞어서)만 만들고 사용자가 20개를 확인. 틀린 사실이 많으면 `PROFILE_MODEL`을 더 큰 모델로 바꿔 다시 시험(비용 확인 후). 통과하면 전체 실행
- 소개와 메타 정보는 **검색과 재정렬 입력에만** 쓴다. 화면에 그대로 보여주지 않는다 (추천 이유는 기존 `/explain`이 실제 데이터 근거로 쓴다) *(내 판단)*

**다시 임베딩:** 새 파일 `data/profile_embeddings.npz` (`ids`, `vectors`, `model_name`, `dim`, `doc_version`). 문서 = `title: {이름} | text: {profile} Mechanics: … Themes: … {설명글 앞 600자}`. 기존 `gemini_embeddings.npz`는 그대로 둔다
- 자연어 검색은 소개 벡터가 있는 게임은 그것을, 없으면 기존 벡터를 쓴다. 평가에서 나빠지면 기존 벡터로 되돌린다

**메타 정보 사용:**
- `keywords`를 `franchise`·`designers`·`designer_countries`와도 단어 단위로 맞춘다 ("Korea" ↔ "South Korea")
- 메타 정보에서 맞는 후보가 하나 이상이면 그 키워드는 **하드 필터** (그 키워드가 메타·이름·설명글에 있는 게임만). 메타에 맞는 게 없으면 2단계처럼 가점만 *(내 판단)*
- 시리즈 묶기: `base_game`이 다른 후보 게임 이름과 맞으면 그 게임과 같은 시리즈

### 5.4 4단계: LLM 재정렬

흐름:
1. 하드 필터 → 점수 → 시리즈 묶기 → 상위 **25개**를 후보 목록으로 (시작값, 평가로 조정)
2. Gemini(`RERANK_MODEL`, 시작 `gemini-3.5-flash-lite`)에 질의와 후보 목록. 게임마다: 이름, 연도, 메커니즘, 테마, 분류, 난이도, 권장 연령, 인원·좋은 인원, 시간, 리뷰 수, 평점, **게임 소개**(없으면 설명글 앞 150자)
3. 응답 (구조화 JSON): `interpretation`("Read as: …" 영어 한 문장, 게임 이름 없이), `ranked_ids`(맞는 순서, 최대 20개, 안 맞으면 빼도 됨), `weak_match`(잘 맞는 게임이 3개 미만이면 true)
4. 서버는 `ranked_ids`를 후보 안 ID로만 걸러 쓰고(중복 제거), 남은 후보를 원래 점수 순으로 이어 붙여 항상 5개를 채운다. 후보 소진 시 404
5. 페이지에 재정렬이 고르지 않은 게임이 섞이면 `weak_match = true`
6. 재정렬 결과에는 `diversify`(MMR)를 적용하지 않는다 (시리즈 묶기가 다양성을 맡음)

규칙:
- 순위 질의(`sort != relevance`)는 재정렬하지 않는다. 해석 문장은 고정 문구: "Ranked by number of BGG reviews." / "Ranked by BGG rating." / "Ranked by release year."
- 재정렬 실패(타임아웃 5초, 파싱 오류, 예산 소진) → 지금 방식 결과, `interpretation = null`
- 캐시: `(query, players, max_time)` 단위로 재정렬 순서 저장. Refresh는 캐시에서. `exclude_ids`가 있는데 캐시가 없으면 다시 호출하되 저장하지 않는다
- 예산: 재정렬도 `gemini.charge()` 1회. 배포 설정의 일일 상한을 낮춘다 (`GEMINI_DAILY_CALL_LIMIT=300`, `deploy-backend.yml`) *(내 판단, 사용자 변경 가능)*
- 추천 이유는 지금처럼 `/explain`. 요청에 `weak_match: bool`(기본 false) 추가. true면 "가장 가까운 점"만 쓰게 한다. 캐시 키에 포함
- 해석 문장에 한글이 섞이거나 200자를 넘으면 버린다

**API 응답 변경** (`POST /search/natural`): 배열 → 객체
```json
{
  "games": [ ...지금과 같은 게임 필드... ],
  "interpretation": "Read as: ..." | null,
  "weak_match": false,
  "web": null
}
```
(`web`은 5단계에서 채움. 4단계에서는 항상 null)

**화면** (`DescriptionSearch`):
```
Results
Matching "할머니, 할아버지와...", 4 players, up to 1 hr
Read as: simple rules, little reading, easy for older adults to join.   ← interpretation

┌ We couldn't find a close match. These are the nearest games. ┐       ← weak_match일 때만
```

### 5.5 5단계: 필요한 질문에만 실시간 웹 검색

**언제:** 질의 해석에 `needs_web: bool` 추가. 우리 데이터와 게임 소개로 답하기 어려운 사실에 기대는 질문만 true. 예: 수상작("스피엘 데스 야레스 수상작"), 디자이너 국적, 특정 출판사, 특정 커뮤니티·국가에서의 인기. 장르·분위기·대상·순위 질문은 false

**흐름 (needs_web일 때만):**
1. 웹 검색 호출 (Gemini `WEB_MODEL`, 시작 `gemini-3.5-flash-lite`, Google 검색 도구, **일반 텍스트 응답**, 타임아웃 8초): "이 요청에 맞는 보드게임의 정식 영어 이름을 한 줄에 하나씩, 최대 15개, 그리고 한두 문장 요약"
2. 서버는 응답의 게임 이름을 우리 데이터의 이름과 맞춘다 (정규화한 정확 일치, ":" 앞 일치). 후보 풀(리뷰 1,000개 이상) 밖이면 무시
3. 맞은 게임은 "웹 일치" 태그로 센다. 조건을 통과한 웹 일치 게임이 5개 이상이면 하드 필터, 적으면 큰 가점 *(내 판단)*
4. 이후는 4단계와 같다 (재정렬 입력에 `web_mentioned: true` 표시)
5. 응답의 `web` 항목: `{ "summary": 웹 검색 응답 텍스트, "suggestions_html": 검색 제안 HTML }`

**약관 준수 (3장):**
- 웹 검색 응답과 그로부터 만든 것(웹 일치 목록, 그 질의의 재정렬 결과)은 **어디에도 캐시·저장하지 않는다**. 로그에도 남기지 않는다. 그 요청의 응답에만 쓴다
- 그래서 웹 검색 질문의 Refresh는 웹 검색부터 다시 한다 (검색 횟수가 늘어나는 것을 받아들인다)
- 화면에 웹 검색 응답 요약과 **Google 검색 제안 위젯**을 결과 위에 함께 보여준다. 위젯 HTML은 고치지 않고, 샌드박스 iframe(`srcdoc`, 링크가 새 탭으로 열리도록 허용)으로 렌더링한다 *(내 판단: 외부 HTML을 페이지에 직접 넣지 않기 위해)*
- 웹 검색 단계는 **자동 평가하지 않는다** (결과 분석·저장 금지). 사용자가 앱에서 직접 확인한다

**비용·실패:**
- 별도 일일 상한 `WEB_SEARCH_DAILY_LIMIT` (시작 100회/일, 환경 변수). 응답의 검색 횟수만큼 차감
- 상한 소진, 타임아웃, 오류 → 웹 검색 없이 진행, `web = null`. 503 아님

**화면:**
```
Results
Read as: Spiel des Jahres winners.
┌ From the web ───────────────────────────────────────────┐
│ <웹 검색 요약 한두 문장>                                    │
│ [Google 검색 제안 위젯]                                     │
└──────────────────────────────────────────────────────────┘
```

### 5.6 테스트

- 가짜 Gemini 클라이언트에 `rerank`, `web_search`, 게임 소개 생성 추가. CI에서 실제 호출 없음
- 2단계: 새 필터·신호, 값 없는 게임 처리, 키워드·단어 일치, 시리즈 묶기와 대표 선택
- 3단계: 소개 JSON 파싱·검증, 이어서 실행, 소개 벡터 우선 사용, 메타 키워드 하드 필터, `base_game` 시리즈 보강, 소개 파일이 없을 때 대체 동작
- 4단계: 후보 밖·중복 ID 무시, 5개 채우기와 `weak_match`, 실패 대체, 순위 질의 재정렬 없음, Refresh 캐시, 응답 형식
- 5단계: `needs_web` false면 웹 호출 없음, 이름 맞추기, 하드 필터/가점 기준, **웹 질의는 어떤 캐시에도 들어가지 않음**, 실패·상한 소진 시 대체, 응답의 `web` 항목
