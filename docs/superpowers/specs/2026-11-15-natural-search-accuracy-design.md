# 자연어 검색 정확도 개선 설계

- 작성일: 2026-11-15
- 상태: 승인됨 (2026-11-15)
- 이전 설계: [2026-11-14-natural-language-search-design.md](2026-11-14-natural-language-search-design.md) (이 문서는 그 위에 쌓는다. 여기서 바꾸지 않은 내용은 그대로 유효)

## 1. 의도와 이유

사람이 보드게임에 대해 할 법한 **대부분의 질문**에 의미가 맞는 게임을 추천하고 싶다. 예:

- 누구와·어떤 자리: "할머니, 할아버지와 함께하기 좋은 게임", "아이와", "술자리에서"
- 느낌·분위기: "긴장감 있는", "머리 안 쓰는"
- 데이터 밖의 사실: "한국인이 만든 보드게임", "스타워즈 테마의 보드게임"
- 답이 없는 질문: "동물들도 이해하기 쉬운 게임"

지금 방식의 한계 (2026-11-15 코드·데이터 확인):

1. **한 방향 흐름이라 결과를 검증하는 단계가 없다.** Gemini 조건 추출 → 설명글 임베딩 유사도 → 고정 공식(`0.75·유사도 + 0.25·평점`). 유사도를 후보 안 중앙값~최댓값으로 환산하므로, 맞는 게임이 없어도 1위는 높은 점수를 받는다. 실패 유형이 나올 때마다 특별 규칙(제목 단어 문제, 순위 질의)을 덧대 왔고, 이 방식은 "모든 질문"으로 확장되지 않는다.
2. **문서가 경험이 아니라 배경 이야기를 담는다.** BGG 설명글은 대부분 설정·홍보 문구다. 질문은 "누구와, 어떤 느낌"을 묻는다.
3. **쓸 수 있는 데이터를 안 쓴다.** `features.load_games()`가 이미 `Family`, `Cat:*`를 붙이지만 자연어 검색은 쓰지 않는다. 원본 `games.csv`에는 권장 연령(`ComAgeRec`), 언어 의존도(`LanguageEase`), 인원별 평가(`GoodPlayers`)도 있다. 후보 2,906개(리뷰 1,000개 이상) 중 거의 전부 값이 있다.
4. **데이터에 없는 사실이 있다.** 디자이너·출판사·국가 정보가 없다 (후보 중 설명글에 Korea가 나오는 게임 3개). 스타워즈는 후보 중 23개가 이름에, 29개가 설명글에 있지만, 추출 프롬프트의 "고유명사를 쓰지 마라" 규칙이 검색문에서 "Star Wars"를 지운다.
5. **같은 게임의 다른 버전이 섞인다.** 후보 안에 Carcassonne 계열 17개, Ticket to Ride 13개, Pandemic 12개. `Family` 열은 값이 하나뿐이고 잘려 있으며("Carcassonn"), 후보 1,318개는 비어 있고, 출판사 라인("Two-player games (Kosmos)")이 섞여 있어 그대로는 묶기에 못 쓴다.
6. **품질을 재는 기준이 없다.** 몇 개 질의를 눈으로 보고 고쳐 왔다.

## 2. 목표 / 비목표 / 실패 기준

### 목표
1. 위 질문 유형에 대해 평가 세트로 **측정 가능한** 정확도 향상
2. 결과 5개 안에 같은 게임 계열은 **대표 하나만** (사용자 결정)
3. 데이터 밖 사실 중 BGG가 가진 것(프랜차이즈, 디자이너, 출판사, 계열)으로 질의 처리
4. 답이 애매하거나 없는 질문에는 **어떻게 해석했는지** 화면에 보여주고, 가까운 결과가 약하면 그렇다고 알림

### 비목표 (이번 범위 밖)
- 검색할 때마다 하는 웹 검색 (Gemini Google 검색 기능). 4단계 평가 뒤에도 남는 유형이 있으면 따로 설계한다
- 게임 문서 보강 (Gemini가 쓴 "플레이 경험 소개"로 다시 임베딩). 평가에서 "상위 40개 안에 정답이 자주 없음"이 확인되면 따로 설계한다
- 검색어 안의 기준 게임 인식("카탄 같은데 더 가벼운"). 이전 설계의 비목표 유지, "By game" 탭이 맡는다 *(내 판단)*
- 2021년 이후 게임, 리뷰 1,000개 미만 게임 (데이터 한계)
- 장르 화면, "By game" 추천의 결과 묶기 ("By game"은 이미 기준 게임과 같은 Family를 뺀다) *(내 판단)*

### 실패 기준 (동작은 해도 실패로 보는 경우)
- 맞는 게임이 없는 질문에 아무 설명 없이 결과 5개를 자신 있게 보여줌
- 해석 문장이나 추천 이유가 데이터에 없는 사실을 지어냄
- Gemini 재정렬이나 BGG 데이터가 실패할 때 검색 자체가 깨짐 (지금 방식으로 물러나야 함)
- 기존 기능(이름 검색, By game, 장르 화면)에 영향
- 화면에 한국어 문장이 나옴
- 결과 표시까지 체감 시간이 크게 늘어남 (기준: 첫 검색 지금보다 +2초 이내, Refresh는 지금과 같음)
- CI가 Gemini·BGG 키를 필요로 하게 됨

## 3. 제약

이전 설계 3장 그대로 (Cloud Run 1Gi, 데이터 파일은 git 커밋, CI에 키 없음, Gemini 유료, 인스턴스당 일일 호출 상한 `gemini.charge()`). 추가로:

- 후보 게임은 리뷰 1,000개 이상 2,906개. 외부 데이터 수집과 LLM 처리 비용은 이 규모 기준으로 잡는다
- BGG XML API는 2025년부터 앱 등록과 토큰이 필요한 것으로 알고 있다. **4단계 시작 전 사용자가 등록하고 이용 약관을 확인해야 한다** (아래 4단계 참고)

## 4. 검토한 방법

| 방법 | 내용 | 장점 | 단점 |
| --- | --- | --- | --- |
| C. 평가 세트 | 다양한 질의 + 정답 게임 목록 + 측정 스크립트 | 모든 변경의 효과를 숫자로 확인 | 정답 목록 만드는 품이 듦 |
| A. LLM 재정렬 | 지금 방식으로 상위 40개를 뽑고 Gemini가 질의에 맞게 다시 고름 | 어떤 표현이든 이해, 답 없는 질문 판단 가능 | 호출 1회 추가, 첫 결과 1~2초 지연 |
| B. 문서 보강 | 게임마다 경험 소개를 생성해 다시 임베딩 | 검색 시 비용·지연 없음 | 지어낸 내용 위험, 재정렬 없이는 검증 단계 없음 |
| BGG 보강 | BGG API로 계열·디자이너·출판사·재구현 관계를 미리 받아 저장 | 데이터 밖 사실과 버전 묶기를 정확하게 해결 | API 등록 필요, 수집 스크립트 |
| 웹 검색 | 질의마다 Gemini Google 검색 | 어떤 사실이든 대응 | 지연·비용, 결과를 데이터와 다시 맞춰야 함, 테스트 어려움, 2021년 이후 게임은 못 보여줌 |
| Gemini 자체 지식 | 검색 없이 LLM이 아는 사실 사용 | 가장 저렴 | 덜 알려진 사실(한국인 디자이너 등)은 지어낼 위험 |

**선택 (사용자 동의): C → 미사용 데이터·프롬프트 → A → BGG 보강 순서.** 웹 검색과 B는 평가 결과를 보고 나중에 판단한다. 이유: 일상 질문(누구와·느낌)은 재정렬과 이미 가진 데이터가 대부분 해결하고, 데이터 밖 사실과 버전 문제는 BGG 데이터가 근본적으로 해결한다. 매 단계 효과는 평가 세트로 확인한다.

## 5. 결정된 동작

단계마다 따로 PR로 합칠 수 있게 나눈다. 각 단계 끝에 평가를 돌려 숫자를 이 문서(또는 `docs/recommendation_pipeline.md`)에 기록한다.

### 5.1 1단계: 평가 세트 (C)

- 질의 파일: `data/natural_eval_queries.json`. 질의 40~60개, 한국어·영어 섞어서, 아래 유형을 고르게:
  누구와·어떤 자리 / 느낌·분위기 / 장르·메커니즘 / 순위("가장 유명한") / 데이터 밖 사실(프랜차이즈, 국가, 디자이너) / 답이 없는 질문 / 버전 중복이 잘 생기는 질의("협력 질병 게임" → Pandemic 계열)
- 항목 형식 (시작안, 세부는 구현자 판단):
  ```json
  {
    "query": "할머니, 할아버지와 함께하기 좋은 게임",
    "type": "audience",
    "players": 4, "max_time": 60,
    "good": [BGGId, ...],        // 이 중 하나 이상이 상위 5개에 있으면 적중
    "bad": [BGGId, ...],         // 나오면 안 되는 게임 (선택)
    "expect_weak_match": false   // 답이 없는 질문이면 true
  }
  ```
  `good` 목록은 후보 2,906개 안의 게임만. 목록이 완전할 수 없으므로 "적중 여부" 위주로 본다
- 정답 목록은 **구현자가 초안을 만들고 사용자가 검토**한 뒤 확정한다 *(내 판단)*
- 측정 스크립트: `backend/evaluate_natural.py` (`uv run python -m backend.evaluate_natural`). 실제 Gemini 키로 돌린다 (CI 아님). 출력:
  - **Hit@5**: 상위 5개에 `good`이 하나 이상인 질의 비율 (유형별로도)
  - **Precision@5**: 상위 5개 중 `good` 비율
  - **Recall@40**: 재정렬 전 후보 40개 안에 `good`이 하나 이상인 비율. 낮으면 문제는 재정렬이 아니라 후보 뽑기 → B를 검토할 근거
  - **중복률**: 상위 5개 안에 같은 계열 게임이 2개 이상인 질의 비율
  - **bad 노출 수**, 답이 없는 질문에서 `weak_match` 판정 비율
- 결과를 JSON으로 저장해 단계별로 비교할 수 있게 한다
- 첫 실행은 지금 코드 그대로 = **기준선**

### 5.2 2단계: 이미 가진 데이터 사용 + 프롬프트 수정

**데이터:** `features.load_games()`가 원본에서 `ComAgeRec`, `LanguageEase`, `GoodPlayers`도 붙인다 (`BestPlayers`는 이미 있음). `LanguageEase`는 값의 척도가 문서와 달라 보인다(21.15 같은 값). 구현자가 의미를 확인하고, 불분명하면 상대 순위(백분위)로만 쓴다.

**조건 추출에 새 항목** (`QueryIntent`):
- `age_max`: "아이와", "8살" 같은 표현 → 권장 연령 상한. 하드 필터, 값 없는 게임은 통과 (난이도와 같은 규칙)
- `categories`: `Cat:Family`, `Cat:Party`, `Cat:Childrens` 등 분류 중 질의가 분명히 가리키는 것. 태그 일치 점수에 포함
- `low_text`: "언어 몰라도", "글 없는" → `LanguageEase` 낮은 쪽 우대 (소프트)
- `keywords`: 질의에 나온 **고유명사**(프랜차이즈, 디자이너, 출판사, 국가)를 영어 정식 이름으로. 예: "스타워즈" → `["Star Wars"]`, "한국인이 만든" → `["Korea"]`
  - `search_text`의 "고유명사 금지" 규칙은 유지 ("마피아 같은"을 장르 설명으로 바꾸는 효과 때문). 대신 고유명사는 `keywords`로 따로 뽑는다
  - 이 단계에서 `keywords`는 이름·설명글 포함 여부로 점수를 올리는 데 쓴다. 4단계에서 BGG 태그 일치로 바뀐다
- 인원 적합도: 화면에서 고른 인원이 `GoodPlayers`에 들어 있으면 소프트 가점 (질의와 무관하게 항상)
- 새 소프트 신호의 가중치는 구현자 판단, 평가로 조정

### 5.3 3단계: LLM 재정렬 (A)

흐름:
1. 지금처럼 하드 필터 → 점수 계산 (2단계 신호 포함)
2. **계열 묶기**(5.4, 4단계 전에는 지금의 `Family` 열과 이름 앞부분으로 임시 묶기) 후 상위 **40개**를 후보 목록으로 (개수는 구현자 판단)
3. Gemini(`EXTRACT_MODEL`과 같은 등급, 상수 `RERANK_MODEL`로 따로 둠)에 질의와 후보 목록을 준다. 게임마다: 이름, 연도, 메커니즘, 테마, 분류, 난이도, 권장 연령, 인원·좋은 인원, 시간, 리뷰 수, 평점, 설명글 앞 300자
4. 응답 (구조화 JSON):
   ```json
   {
     "interpretation": "Read as: simple rules, little reading, easy for older adults to join.",
     "ranked_ids": [BGGId, ...],   // 질의에 맞는 순서, 최대 20개, 맞지 않는 게임은 빼도 됨
     "weak_match": false            // 후보 중 질의에 잘 맞는 게임이 거의 없으면 true
   }
   ```
5. 서버는 `ranked_ids`를 후보 목록 안의 ID로만 걸러 쓴다. 그 뒤에는 남은 후보를 원래 점수 순으로 이어 붙이고(재정렬이 뺀 게임 포함, 40개 밖 후보까지), 그래서 항상 5개를 채운다. 후보가 모두 소진되면 지금처럼 404 *(내 판단)*
   - `ranked_ids`가 5개 미만이면 `weak_match`를 자동으로 true로 둔다 (첫 페이지에 재정렬이 고르지 않은 게임이 섞이므로) *(내 판단)*
6. 기존 `diversify`(MMR)는 재정렬 결과에는 적용하지 않는다 (LLM 순서를 존중, 계열 묶기가 다양성을 맡음) *(내 판단)*

규칙:
- **순위 질의(`sort != relevance`)는 재정렬하지 않는다.** 지금 동작(리뷰 수·평점·연도 순)이 잘 되고, LLM이 순서를 흐트러뜨릴 이유가 없다. `interpretation`은 서버가 고정 문구로 채운다 (예: "Ranked by number of BGG reviews")
- **재정렬 실패**(타임아웃, 파싱 오류, 예산 소진) → 503이 아니라 지금 방식 결과로 응답. `interpretation`은 `null`
- **시간 제한**: "+2초"는 보통의 경우 기준이다. 재정렬 호출은 별도 짧은 타임아웃(시작 5초, 상수)을 두고, 넘으면 위 실패 대체로 간다 *(내 판단)*
- **캐시**: `(query, players, max_time)` 단위로 재정렬 결과 전체 순서를 저장. Refresh(`exclude_ids`)는 캐시된 순서에서 다음 5개를 꺼내므로 Gemini 호출 없음
- **캐시 미스 Refresh** (다른 인스턴스로 갔거나 캐시에서 밀려남): 재정렬을 다시 호출해 캐시를 채운다. `exclude_ids`가 있으므로 이미 본 게임은 다시 나오지 않는다. 드문 경우라 지연을 받아들인다 *(내 판단)*
- 예산: 재정렬도 `gemini.charge()` 1회
- 추천 이유는 지금처럼 `/explain`(mode `query`)이 따로 만든다 *(내 판단: 재정렬 호출에 이유까지 합치면 호출 수는 줄지만, 순위 질의·Refresh·실패 대체가 복잡해진다)*
  - 단 `/explain` 요청에 선택 항목 `weak_match: bool`(기본 false)을 추가한다. true이면 프롬프트가 "질문을 다 만족한다"고 쓰지 말고 **가장 가까운 점이 무엇인지**만 쓰게 한다. 프론트는 검색 응답의 `weak_match`를 그대로 넘긴다. 캐시 키에 포함 *(내 판단: 프롬프트만으로는 약한 일치인지 알 수 없어서 지어낸 이유가 나온다)*
- 해석 문장·이유 모두 영어. 해석 문장도 기존 `explain.py`처럼 한글이 섞이면 버린다

**API 응답 형식 변경** (`POST /search/natural`): 배열 → 객체
```json
{
  "games": [ ...지금과 같은 게임 필드... ],
  "interpretation": "Read as: ..." | null,
  "weak_match": false
}
```
조건에 맞는 후보가 아예 없으면 지금처럼 404.

**화면** (`DescriptionSearch`):
```
Results
4 players · up to 1h · "할머니, 할아버지와..."
Read as: simple rules, little reading, easy for older adults to join.   ← interpretation (있을 때만)

┌ We couldn't find a close match. These are the nearest games. ┐       ← weak_match일 때만
```
- 해석 문장은 결과 제목 아래 한 줄, 기존 보조 글씨 스타일
- `weak_match` 알림은 지금의 "newest" 알림과 같은 상자 스타일

### 5.4 4단계: BGG 데이터 보강 + 계열 묶기

**선행 조건 (사용자):** BGG XML API 앱 등록, 토큰 발급, 이용 약관 확인. 토큰은 로컬 환경 변수 `BGG_API_TOKEN`으로만 쓰고 배포 서버에는 넣지 않는다 (수집은 한 번만, 결과 파일을 커밋). 등록이 안 되면 5.4의 "등록 불가 시"를 따른다.

**수집 스크립트:** `backend/build_bgg_meta.py` → `data/bgg_meta.json`
- 대상: 후보 조건(리뷰 1,000개 이상)을 통과하는 게임. 여유를 두려면 리뷰 500개 이상(4,688개)까지 *(내 판단: 500개 이상, 나중에 후보 기준이 바뀌어도 다시 받을 필요 줄임)*
- 게임마다: 계열(boardgamefamily) 이름 목록, 디자이너, 출판사, 재구현 관계(reimplements / reimplemented by), 컴필레이션 관계
- BGG 서버에 부담을 주지 않게 요청 간격을 두고, 재시도·중간 저장(이어서 실행) 지원. 간격·묶음 크기는 BGG 안내를 따른다

**계열 묶기 (버전 중복 제거):**
- **묶는 범위: 시리즈 전체** (사용자 결정, 2026-11-15). 다른 판(Big Box, 기념판, 지도판)뿐 아니라 **후속작·스핀오프도 한 묶음**이다. 예: Pandemic + Pandemic Legacy 시즌 0~2 + Pandemic: Iberia, Codenames + Codenames: Duet, Gloomhaven + Jaws of the Lion
- 같은 계열 = 재구현 관계로 이어진 게임 + BGG 계열 중 **게임 시리즈 유형**("Game: Carcassonne" 같은)을 공유하는 게임. 국가·테마·출판사 라인·미디어 계열("Country: …", "Theme: …", "Movies: …" 등)로는 묶지 않는다. 정확한 접두어 규칙은 실제 데이터를 보고 구현자가 정한다
- 평가 세트의 중복률과 `good` 목록도 이 범위를 따른다 (같은 시리즈 둘이 상위 5개에 있으면 중복)
- **대표 선택:** 필터를 통과한 같은 계열 후보 중 **리뷰가 가장 많은 버전**. 단, 질의의 `keywords`·태그와 일치하는 버전이 있으면 그 안에서 고른다 (예: "스타워즈" 질의에서 Carcassonne 계열 대표는 원판이 아니라 "Carcassonne: Star Wars") *(내 판단)*
- **순위 질의**(`sort != relevance`)에서도 묶기를 하되, 대표는 리뷰 수가 아니라 **정렬 기준 값이 가장 높은 버전**이다 (예: "평점 높은" 질의에서 Pandemic 계열 대표는 평점이 가장 높은 버전) *(내 판단)*
- 묶기는 재정렬 후보 목록(40개)을 만들기 **전에** 한다
- 상세 팝업(`GameDetailModal`)에 **"Other versions"** 목록: 같은 계열의 다른 게임 이름·연도, 누르면 그 게임 상세로. `GET /games/{bgg_id}` 응답에 `OtherVersions: [{BGGId, Name, YearPublished}]` 추가 (계열이 없으면 빈 배열)

**데이터 밖 사실 질의:**
- 2단계의 `keywords`를 BGG 태그 이름과 맞춘다. 단어 단위 일치(부분 문자열 아님, "Korea"는 "Korea Boardgames"의 단어로는 맞지만 아래 규칙으로 걸러짐)
- **하드 필터는 계열(프랜차이즈·국가·시리즈)과 디자이너 일치에만** 건다. 출판사는 현지화 출판사(예: "Korea Boardgames", "Hobby Japan")가 인기 게임 수백 개의 번역판을 내므로 **가점만** 준다 *(내 판단)*
- 맞는 태그가 없으면 2단계처럼 이름·설명글 가점으로 물러난다
- "한국인이 만든": BGG의 국가 계열이 디자이너 출신을 뜻하는지, 배경 국가를 뜻하는지 데이터를 받아 확인한다. 디자이너 출신 정보가 없으면, 한국 출판사 계열이나 디자이너 정보로 근사하고 그 한계를 평가 결과에 적는다
- 재정렬 후보 정보에 디자이너·출판사·주요 계열도 넣는다

**등록 불가 시 대체:** 계열 묶기는 지금의 `Family` 열(출판사 라인 값 제외 목록 포함) + 이름 앞부분(":" 앞) 일치로 근사. 데이터 밖 사실은 2단계 `keywords` 가점까지만. 이 경우 "한국인이 만든" 유형은 해결되지 않는다고 평가에 기록한다.
